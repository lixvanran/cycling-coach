## 3. AI 突破点 (Track 2)

### 5 个 daily driver 场景的 AI 突破

每个都做到"TP 永远做不到"的体验差距。

#### AI-1: "今日该练什么？" (dashboard 第一卡)
- **场景**: 用户每天打开 cycling-coach 第一个看到的
- **输入**: 当前 TSB/CTL/ATL + 未来 7 天 planned + 上周实际
- **输出**: AI 推荐训练（含理由）→ 一键加入 Calendar
- **为什么 TP 做不到**: TP 永远要用户自己看数据想意思

#### AI-2: "AI 帮我排下周课"
- **场景**: 用户周日晚上想下周计划
- **输入**: "下周有 X 比赛" + 当前 fitness + 历史强度
- **输出**: 多 mind workflow 生成候选人课表 → 用户确认 → 写入 Calendar
- **为什么 TP 做不到**: TP 的 Plan 是 template-based, AI 是 dynamic reasoning

#### AI-3: 训练后 AI 1 句话点评
- **场景**: 训练完同步过来
- **输出**: Toast 推送 "今天 IF 偏高，间歇过硬了 — 注意 Z3 占比"
- **为什么 TP 做不到**: TP 是静态数据展示, 我们是 dynamic coach

#### AI-4: ACWR/TSB 警告 + AI 解释
- **场景**: ACWR > 1.5 或 TSB 转负很大
- **输出**: 不是数字警告, 是"为什么 + 怎么办" (基于 KB 潘震内容)
- **为什么 TP 做不到**: TP 警告是阈值数字, 我们是 actionable advice

#### AI-5: AI 战术对话 (Race Tactics 增强)
- **场景**: 用户上传比赛路书 PDF/PNG + 提问
- **输入**: 路书 + "这个爬坡怎么配速"
- **输出**: AI 解读路书 + 给出 pacing 策略 + 写回 race_plan
- **为什么 TP 做不到**: TP Race Day 是 template, 我们是 LLM 推理

### AI 突破的关键路径

**Daily driver 顺序**: AI-1 (每天用) > AI-3 (每周用) > AI-4 (偶尔触发) > AI-2 (周日晚) > AI-5 (备赛时)

**资源优先级**: AI-1 + AI-3 + AI-4 是 **daily driver**, 投入最高
AI-2 + AI-5 是 **event-driven**, 投入其次

## 6. 第一个月做什么 (具体到 task)

### Week 1-2: Drop folder watcher
- 新建 `cycling_coach/core/sync/folder_watcher.py`
- 平台适配: macOS FSEvents / Linux inotify / Windows ReadDirectoryChangesW
- 用 watchdog Python lib（跨平台成熟方案）
- 配置位置: `~/Library/Application Support/cycling-coach/inbox` (mac) / `~/.local/share/cycling-coach/inbox` (Linux) / `%APPDATA%/cycling-coach/inbox` (Windows)
- 后台服务模式: 提供 systemd / launchd / Windows Service 安装脚本
- 自动解析: 复用 `data/parsers/fit_parser.py`
- 去重: 按文件 hash + activity 时间

### Week 3: 移动响应式 (Sidebar 抽屉 + Calendar 重排)
- 全局媒体查询: `< 768px` 重排
- Sidebar: 抽屉 pattern (汉堡按钮 toggle)
- Calendar: 月视图 → 周视图 → 日视图 (Tab 切换)
- 字号 / 间距: mobile 适度紧凑

### Week 4: AI-1 数据层 ("今日该练什么" 推理模块)
- 新建 `cycling_coach/ai/recommendations/today.py`
- 输入聚合器: `core/services/dashboard_context.py` (TSB/CTL + 7 天 planned + 1 周 actual)
- 推理 prompt: 把 context 转 LLM-friendly JSON + 问 "今日练什么"
- 输出 schema: `{ recommended_workout: {...}, reasoning: "..." }`
- 测试: 用历史数据回放, 看推荐合理性

## 7. 关键决策

### Q1: Garmin 直连怎么实现?

**3 个方案**:
- **A. Drop folder watcher** — 用户丢 FIT 进文件夹, 自动导入。**0 摩擦, 但用户得自己导出**。
- **B. Strava webhook** — 用户授权 Strava, 新活动自动拉。**0 摩擦, 但要先有 Strava**。
- **C. Garmin Health API** — 直连 Garmin 云。**需要 OAuth 申请, 工作量大**。

**推荐**: 先 A + B (1-2 周搞定), 后 C (作为 V1.0 项)。
**理由**: 80% 用户已经习惯 Strava 中转, drop folder 兜底。

### Q2: Mobile App 还是 PWA?

**PWA**:
- 0 摩擦: 浏览器打开, "添加到主屏幕" 就是 App
- 离线访问: service worker 缓存 KB
- 推送: Web Push API (后端推送训练提醒)
- 维护成本: 跟 web 一起改

**Native App**:
- BLE/ANT+ 直连设备 (推 workout 到 Zwift / Garmin Edge)
- 后台运行 (训练实时同步)
- 但维护成本翻倍

**推荐**: PWA (V0.9.0), Native App 永不做。
**理由**: 我们定位是 desktop-power-user, mobile 是"看 + 轻操作", PWA 足够。

### Q3: 课程库从哪里来?

**3 个来源**:
- **A. KB 里挑训练学结构** — 我们已有 155MB 训练百科, 里面结构化课程 (sweet spot, threshold 等)。挖出来。
- **B. TrainerRoad 公共结构** — 他们的课程结构是公开的训练学, 借鉴 metadata, 不抄原文。
- **C. AI 生成** — 用 chat.py prompt 生成, 但生成的内容需要人工 review 才进 library。

**推荐**: A 70% + B 30%, AI 生成只做"用户自建 + 分享"。
**理由**: 已有资产 + 公开结构 = 0 成本, 200+ 课程 2 周搞定。

## 8. 风险与不做项

### 已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| Garmin API 申请被拒 | M1 阻塞 | drop folder + Strava 兜底 |
| 移动响应式回归 | 老 UI 变形 | 一开始就 mobile-first 设计, 桌面只是放大版 |
| AI 推荐不靠谱 | 用户不信 | 提供"理由"展示, 让用户能 override |
| 课程库审查质量 | 训练学错误 | 内部 review, 用户反馈闭环 |

### 明确不做 (划线)

- ❌ 多运动员 / 教练协作
- ❌ 社交 / Feed / Follow
- ❌ Premium paywall
- ❌ 原生 iOS/Android App
- ❌ 重写后端微服务化
- ❌ 直接 Garmin BLE/ANT+ 协议推 workout
- ❌ 多语言 i18n (除非有海外用户需求)
