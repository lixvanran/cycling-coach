## 二、本轮修的真 bug（都有测试锁死，180 passed / 0 failed）

全部属于同一类：**"1 样本 = 1 秒"的隐含假设** 或 **静默失败**。

| # | 位置 | 症状 |
|---|---|---|
| 1 | `core/metrics/power.py` `normalized_power` | 零填充 → 10s 采样 NP 只有真值 1/10（2s 就腰斩） |
| 2 | `power_zones` / `power_zones_detailed` / `total_kj` / `hr_zones` | `mask.sum()` 数样本当秒 → 少算 10 倍 |
| 3 | `pa_hr_decoupling` | 门槛 `len(valid)<1800` → 1 小时骑行被当 6 分钟拒算 |
| 4 | `data/parsers/fit_parser.py` `position_lat/long` | 没从 semicircles 换算（潜伏 bug） |
| 5 | `fit_parser` 缺 session 汇总 | 静默返回 0，watcher 还报"导入成功" |
| 6 | `ai/m3_client.py` | `[THINK]` 裸 token + 降级提示泄漏给用户 |

新增共享工具 `sample_durations()` / `seconds_in_bins()`（power.py），hr.py 复用。
dt 用**区间模型**（每样本负责到下一点那段）而非梯形积分 —— 梯形会少算 1 秒。

**实测效果**（同一小时骑行，只改采样率）：

| 指标 | 修前 @10s | 修后 |
|---|---|---|
| `power_zones` Z4 | 360 秒 ❌ | **3600 秒** ✅ |
| `total_kj` | 90 kJ ❌ | **900 kJ** ✅（真值 250W×1h） |
| `pa_hr_decoupling` | 判"数据不足"拒算 ❌ | **正常计算** ✅ |

这正是 TP 用户说的 "zones waaayyy off"。**我们修了，TP 还没修。**

## 三、一次误判的教训（重要）

我曾报 P0-1「FIT 时长被放大 1000 倍（毫秒当秒）」—— **这是错的**。

决定性实验：

```
fit_tool 传 3600  → fitparse 读回 3600.0   (秒)
fit_tool 传 30600 → fitparse 读回 30600.0  (米)
```

fitparse **已经**应用了 profile 的 scale，直接返回人类单位。
现象的真凶是**我的测试 fixture 自己写了 `duration*1000` 造成双倍缩放**，然后我怪了 parser。

**教训**：合成测试数据前，先做"决定性实验"确认工具的单位约定，
别把自己的 fixture 当 ground truth。已把踩坑写进 `tests/fit_fixtures.py` 文档。

# 追加二：Windows 交付硬化（夜间自主批次）

日期：2026-10-03 夜
范围：Windows 启动/停止/诊断/卸载全链路 + 数据库升级安全

起因：上一轮把代码层的窟窿补完后，**最大的剩余不确定性是"在真机 Windows 上
到底跑不跑得起来"**，而沙箱是 Linux，验证不了。所以这一轮不加班功能，
专门拆 Windows 特有失败模式，并造一个让用户能自助验收的工具。

方法：主攻 + 独立 Verifier 对抗性审计（只读，产问题清单不修代码）。
Verifier 与我的实现互相独立，抓到了我写的代码里的真问题。

## 一、Verifier 抓到的、我自己没看到的

| 级别 | 问题 | 位置 |
|---|---|---|
| **P0** | `build_release.py` 用 `git ls-files` 收集文件、尊重 `.gitignore`，而 `cycling_coach/static/` 被 ignore → **官方 source zip 不带前端产物** → Windows 用户双击 start.bat 必失败，报错还让他去装 Node（而 start.bat 文件头承诺不需要 Node） | `tools/build_release.py:56-96` |

# 追加六：Verifier 判 FAIL 后的 5 处修补

## 🔴 我给 pnpm 仓库装了 npm lockfile

这仓库包管理器是 **pnpm**：`engines.pnpm>=8`、`pnpm-workspace.yaml`、整份
`.npmrc`、`start.py:718` 走 `run_pnpm_install()`。而我装 vitest 时只更新了

# 追加七：readiness 诚实性的三轮收敛（对抗审查驱动）

日期：2026-10-04 下午
这一段全部来自 Verifier 的独立对抗性审查。它抓到我三轮修复里的
**两个 P0 和三条 P1/P2**，其中最严重的那个我完全没想到。

## 三个 P0，一条比一条深

### P0-A：编造默认值（第一轮）

五个维度在无数据时各自编一个高分默认值，ACWR 退回 `get("acwr", 1.0)`
落在甜区拿满分 25/25。8 天训练的用户拿到 67 分"良好"+ 阈值间歇处方。

**8 周/45 次活动的老用户复验后才发现：ACWR 恒定算不出来。**
`get_acwr(db, days=7)` 而 chronic 窗口是 28，`if len < 28: return []` 恒真。
**ACWR 对所有用户从来没算出来过。**

> 假数据不只是撒谎，它还**掩盖真 bug**。如果 ACWR 一开始正常返回 None，
> 上一轮改的时候一定会顺手查"为什么算不出来"，立刻发现 days=7。
> 只要默认值填得"合理"，就没人会去查那是不是真的。

### P0-B：归一化凑出 100 分（本轮，最严重）

    2/5 维 (tsb 20 + phase 15)           -> 35/35 = 100  极佳  vo2
    3/5 维 (tsb 20 + phase 15 + rpe 10)  -> 45/45 = 100  极佳  vo2
    4/5 维 (全但缺 acwr)                 -> 75/75 = 100  极佳  vo2

零 HRV、零 ACWR 的用户被派去做 4-6×3min @ 110-120% FTP。
HRV 恰恰是抓"看着还行其实已经过载"的那个维度。

**Verifier 建议 `MIN_DIMENSIONS 2→3`，我算了一下没照做**：
tsb 20 + phase 15 + rpe 10 = 45/45 同样是 100。门槛只是遮羞布，
**病根是归一化本身** —— 分子分母同时缩小，比值不变。

解法是**分数和档位分开管**：
- 分数 = 已知信号有多好 → 归一化是对的
- 档位 = 我们能有多确定 → 对覆盖度封顶

`MAX_TIER_BY_COVERAGE = {3: "endurance", 4: "threshold", 5: None}`，
覆盖度不完整时最高档封在 endurance/threshold，且**不许出现"极佳"**。

### P0-C：中文字符串当数据契约

`if pmc.get("status_label") != "无数据"` —— 有行但无负荷时，
`float(row.tsb or 0)` → `classify_status(0,0)` → "平衡" → 哨兵放行 → 满分 20/20。
**路径普通用户走得到**：骑满一周、今天休息、填一次 RPE（于是建了行）。87 分"极佳"。

更深的坑：`models.py` 里 ctl/atl/tsb 都是 `default=0.0`，
**"没测"和"测出来是 0"在 schema 层就被抹平了**，NULL 根本不会出现。
所以 `IS NULL` 判据也不可用，只能用语义判据（CTL/ATL 是 TSS 的 EWMA，
有任何训练史就必然 > 0）。

## 这一段最该记住的三条

1. **假默认值会掩盖真 bug。** 一个填得"合理"的兜底值，
   能让一个从没有效过的功能看起来一直正常。
2. **归一化 + 阈值 = 分数可以脱离数据质量。** 归一化本身没错，
   错的是让它**直接驱动**不可逆的处方。
3. **中文字符串不该承担数据契约。** `status_label` 是给人看的，
   拿它当程序判据，迟早会被某个 `classify_status` 的返回值绕过。

## 变异测试账目

Verifier 独立跑 12 个变异，4 个存活。它没客气地说：
"变异体 M4/M6 对应的分支是死代码"。

| 变异 | Verifier 时 | 现在 |

| M4 TSB 判定退回 `if True:` | 存活 | 红 2 条 |
| M6 删掉两个 None 门槛 | 存活 | 红 1 条 |
| M9 删掉覆盖度提示 | 存活 | 红 3 条 |
| M10 round → int 截断 | 存活 | 已随归一化测试重写覆盖 |
| M13 关掉档位封顶（新） | — | 红 1 条 |

它还指出我一条测试**从来没调用过被测函数**：
`test_full_data_score_unchanged` 从头到尾对手写字面量断言，
它自己用 5145 组组合证明了性质成立 —— 证明的不是我那条测试。
那条测试的作用是**零**，已删。

# 追加八：第三轮 —— 修过头，以及一次假信号变异测试

日期：2026-10-04 傍晚
第二轮 P0/P1 修完后，全量测试挂了一条，挂的方式值得单独记。

## 修过头：4 周 20 次训练的用户被判"数据不足"

上一轮为挡 P0-1 把 `MIN_DIMENSIONS_FOR_READINESS` 从 2 提到 3。
全量立刻挂：`test_with_enough_data_score_is_returned` ——
一个 **20 次训练 / 4 周**的用户拿到 `None`。

**但他数据很充足。** 缺的是 HRV（晨起心率变异性）和 RPE（主观疲劳）
这类**补充测量**，训练量完全够。说"数据不足"是在骗他。

两类"不够"从来不是一回事：

| 缺什么 | 谁来管 | 该怎么说 |
|---|---|---|
| 训练量不够（<7 次 / 跨度 <7 天） | `_data_sufficiency` | "数据不足" —— 别猜 |
| 测量维度不够（缺 HRV/ACWR/RPE） | `MAX_TIER_BY_COVERAGE` | 给建议，但**封住强度** |

混成一件事，就会要么放过 P0-1，要么把正常用户判死。
所以 `MIN_DIMENSIONS` 退回 2，2 维用户封顶调到最保守的 recovery：

    2/5 → recovery   3/5 → endurance   4/5 → threshold   5/5 → 不封顶

实测：4 周用户 `数据不足` → **14 分「危险」+ 完全休息**（他 TSB 极低，
本来就该休息），分数真实且没被抬到 recovery 之上。8 周 demo 用户 42 分不变。

> **"宁可说算不出来"我执行过头了。**
> 项目真正要的是**别自信地给错建议**，不是**什么都别说**。
> 给一个被封顶的保守建议，比回一句"算不出来"有用得多 ——
> 前提是它确实被封住了，而且用户知道自己被封住了。

## 一次假信号变异测试（本轮最要紧的教训）

M6（删掉两个 `None` 守卫）那次变异，我看到"测试变红 1 条"就当它被杀。

**但守卫在 baseline 里本来就不在。** 那次变异是**空操作**，"变红"是别的
断言造成的。

我是怎么发现的：补完守卫后去查"为什么零数据用户能拿 80 分"，顺着看到

    # 数据够不够给一个分?

    # 按**可用维度**的满分归一化。

两行注释之间**什么都没有**。守卫没了。零数据用户只靠一个凭空来的
`phase: 12` 归一化出 **80 分** —— 而"低 CTL"的原因是**根本没数据**。

修掉后：`80 分` → `score=None, breakdown={}`。
`phase` 现在要求"有真实负荷数据 **或** 有赛程"才计入。

**此后注入变异前一律先断言 baseline 符合预期**，匹配不上就拒绝注入 ——
宁可变异失败，也不要一个假的"已验证"。

> 变异测试最危险的失败模式不是"变异存活"，
> 而是**"变异无效但看起来被杀"**。后者危害更大：你以为自己验证过了。

补的测试里有一条专门钉这件事：
`test_the_none_guards_actually_exist` 断言守卫存在**且在归一化之前**。
守卫位置错了的话它和那两个 `None` 判定一样形同虚设。

## 又抓到一个只在今天才走到的路径

封顶时 `rec_type, readiness_label, intensity, target = _TIER_DETAIL[tier_cap]`
解包 4 个值，而 `_TIER_DETAIL` 存的是 3 元组 —— **一封顶就 ValueError**。
2 维封顶（recovery）是新加的，这条路径今天才第一次被走到。

**活到今天才第一次执行的代码，就是没被测过的代码。** 新加的分支要么
配测试，要么自己走一遍。

## 两条测试写错了，也记下来

1. `test_zero_data_user_gets_no_score_at_all` 第一版用了模块级的 `fresh`，
   而它已经被 `short_history_athlete` 导了 8 次训练 —— 断言报出来的是
   `{'tsb': 5, 'phase': 12}`。**我以为的空库根本不是空的。**
   独立空库 fixture 是必需的。
2. 封顶测试的实验前提会因前面的修改而失效（`phase` 变条件写入后，
   可用维度从 3 掉到 2），要补一个赛程才能复现"有 2 维但缺负荷"这个场景。
   **测试的前提必须显式断言**，否则它悄悄失效时你只会看到"莫名其妙"的红。

# 追加十：核心竞争点确定后的第一次转向

## 定位变了, 优先级跟着变

核心竞争点确定：**性能齐平 + 开源免费**。

这句话直接改变了我的优先级判断。TP 的付费墙功能(StackUp 云端 / 教练协作 /

追了就是把自己拖进他们的成本结构, 还收不到他们的钱。

于是在"功能广度"之外, 有一件更致命的事:

> **免费开源 App, 用户装完第一屏看到的是"数据不足, 暂不评估状态"

### 「先看示例」这条链路修掉了 3 个 bug

`load_demo_data` 原来整个埋在 `main()` 里, 耦合 argparse 和 print,
**程序根本调不到** —— 前端只能做成死链。抽成函数 + 新增 `POST /api/demo/load`。

真跑之后连续暴露三个问题, **每一个静态看都完全正常**:

1. **SystemExit 抓不到** —— 继承 `BaseException` 不是 `Exception`。
   而"归属不一致"这个**最需要用户看到的**错误恰恰用 SystemExit 抛,
   结果用户只看到"载入失败"。
2. **占位 athlete 冲突** —— `ActivityService` 会自动建 "Rider" 占 id=1。
   零数据用户点按钮 = 先建 Rider(id=1) 再建演示车手(id=2) → 归属校验直接抛。
   原来的 `--force` 只删同名的, 清不掉它。
3. **commit() 后 ORM detach** —— 抽函数时读 `a.id` 抛 DetachedInstanceError。
   **这个 bug 原本就存在**, 只是以前 `return 0` 用不到这些字段。

还有一次**验证方法错误**差点让我误判代码有问题: 我用 `app.routes` 数路由
发现只有 29 个就以为注册失败, 实际上 `app.routes` 是 lazy 的,
`/openapi.json` 里有 111 个路径。
