# 公路自行车 AI 教练 · Cycling Coach

**本地优先、开源免费、对数据诚实**的公路车训练分析工具。

对标 TrainingPeaks 的核心训练分析能力，Windows 桌面本地运行，数据不出本机。

---

## 一句话说明它是什么

导入 Garmin / Wahoo 的 FIT 文件，得到 TP 同级别的训练负荷分析（CTL/ATL/TSB、功率区间、能量分布），
外加一个基于 359 篇专业资料的中文 AI 教练。

**它不会在你没测 FTP 时假装知道你的 FTP，也不会在数据不足时给你一个看起来很权威的分数。**

---

## 核心原则：缺数据 ≠ 编一个像样的值

这是这个项目和其他"看起来很完整"的工具最大的区别，也是我们花最多力气的地方。

| 场景 | 常见的做法 | 本项目的做法 |
|---|---|---|
| 零训练数据 | 训练负荷显示 `CTL 0.0` | 「还没有带功率的训练记录」 |
| 零数据 readiness | 归一化给个 82 分"极佳" | 算不出就是 `null`，并说明缺哪几个维度 |
| 只有 RPE 的休息日 | 训练负荷维度照常计分 | 识别为"无负荷数据"，不占分数 |
| 数据不足时的目标 TSS | `0`（看起来像"今天免练"） | `null` + 界面显示"目标待定" |
| 只有 2/5 个维度可用 | 归一化出 100 分"极佳" | 封顶 70 分 |
| 没有 FTP | 沿用默认 250W | 用**估算值**算并标记 `用估算=True`，或明确说算不出 |
| 0 训练时打印"今日计划" | 打印空计划 | 打印"无计划"并链接 FTP 输入指引 |

这些不是设计文档里的口号，是 `tools/scan_data_honesty.py` 每次运行机器校验的。

**但要说清楚它覆盖到什么程度** —— 产品有 133 个接口操作（113 条路径），
扫描器实际覆盖 **58 个，约 44%**：

- ✅ 覆盖：无路径参数的 GET（79 个 GET 里的 58 个）
- ❌ **不覆盖：所有写操作**（POST / PATCH / DELETE，合计 54 个）——
  上传、写计划、导入等一律不扫
- ❌ 不覆盖：带路径参数的 GET（17 个，如 `/api/activities/{id}`）
- ❌ 不覆盖：strava（4 个）/ static 等被排除的路径

所以它是**防回归的护栏**，不是全面保证。写操作的诚实性目前靠
逐个 review 和专门的测试保证。

> 这段说明本身是 Verifier 复审逼出来的 —— 我原来写的是"扫 107 个端点"，
> 既和同一份文档里另一处的"58"自相矛盾，也是一个**虚假覆盖率声明**。
> 在一个卖点是"不编造"的项目里，夸自己的检查力度比不检查更糟。
>
> V0.9.1 又按当前 `e48703a` 的 OpenAPI 重新数了一遍（V0.9.0 写这行时
> 产品还在加接口，数字就已经漂了）：127→133 操作、107→113 路径、
> 75→79 GET，覆盖率 46%→44%。**58 这个数字本身没变** ——
> 它是按同一套过滤规则数出来的，不是拍脑袋写的。

## 快速开始（Windows）

### 前提

- Python 3.11+
- **不需要装 Node.js**（前端已随源码包提供）

### 三步

```bat
:: 1. 解压到短路径（重要：知识库里有长路径名，别放太深）
mkdir C:\cc
:: 把 zip 解压到 C:\cc  —— 用命令提示符解压到 C:\cc，
:: 不要双击 zip 让资源管理器解到"下载"目录（路径会变长，逼近 260 字符上限）

:: 2. 双击 tools\ACCEPTANCE_CHECKLIST.bat
::    它会一步步带你走：装依赖 -> 自检 -> 启动 -> 检查界面
::    每一步都有明确的"通过/停在这里"，出问题会告诉你报告在哪

:: 3. 日常使用就双击 tools\start.bat
```

> ⚠️ **如果你要手动敲命令启动，必须带 `--desktop`**：
>
> ```bat
> python tools\start.py --desktop
> ```
>
> 不带的话会进开发模式，试图启动 Vite —— 而 **Windows 上你没装 Node.js**。
> `start.bat` 会自动加上这个参数，但手动敲时容易漏。

`start.py` 会自动完成：建虚拟环境 → 装后端依赖 → 拉起服务 → 打开浏览器。
**不需要你手动 pip install。**

### 第一次用

1. **先看示例** — 首页有「先看示例」按钮，一键灌入 8 周真实结构的演示数据，
   立刻能看到完整界面长什么样，不用先啃文档。
2. **或者直接导入 FIT** — Garmin / Wahoo 的 `.fit` 文件，拖进去就行。
3. **去「数据 → 数据可信度」** — 那一页会告诉你：哪些数据有、哪些缺、缺的原因、以及每个算法的文献出处。

### 建议顺手填一个 FTP

不填也能用（会用估算值并标明），但填了之后解锁：功率区间、时间在各区间分布、
能量分布（polarization）、以及 AI 引用具体数字时不用再含糊其辞。

## 功能

### 训练数据

- FIT 自动导入（Inbox 文件夹监听 / 手动上传 / 命令行）
- 功率区间、能量分布、训练负荷（CTL/ATL/TSB/ramp rate）
- 训练计划与实际对比、周期化（Phases）
- 日历视图、趋势、两条训练对比
- 手记 / 日记

### AI 教练

- 中文对话，基于 **359 篇**专业资料（RAG）
- 回答会引用具体文献出处
- 上下文注入你**真实**的训练数据——没有的数据会明确告诉 AI"无数据"，
  而不是塞一个 0 让它照着编

### 数据可信度（V0.9.0 新增）

这是我们认为最被低估的功能。`/数据/数据可信度` 会告诉你：

- 每个数据维度的覆盖率
- 缺失的具体原因
- 每个指标的算法出处（文献链接）
- 产品在"数据不足"时的明确策略

**一个不敢告诉你哪里不完整的数据工具，不值得信任。**

## 已知限制

说清楚比藏着好。

- **Windows 真机尚未验证。** 全部开发、测试、打包都在 Linux 上完成。
  Windows 路径（自启动、中文字体、`--desktop` 静态模式）都只做到了
  "代码里写对了"，**没有在真 Windows 机器上跑通过一次完整流程**。
  第一次用请按 `INSTALL_V0.9.0.md` 走一遍，有问题直接报。
- **时区按运行机器的当前时区算日桶。** `pmc.py` 里 `astimezone()` 不带参数
  就是用运行机器的本地时区，所以**出差改系统时区后，同一批历史骑行会按新时区
  重新分日**。正解是给车手配一个时区设置（`athlete.timezone`）并按车主的时区
  分桶 —— **没实现**。跨时区出差期间的历史数据会看起来"不对"，这是已知行为，
  不是数据坏了。
- **诚实性扫描器只覆盖 58 个 GET 端点**（占 133 个接口操作的 44%）。
  所有 POST / PATCH / DELETE 一律不扫 —— 上传、写训练计划、导入这些
  写路径的诚实性，靠的是逐个 review + 专门的回归测试，**不是**机器校验。
- **仅 Windows 桌面优先**。macOS / Linux 未做正式验证。
- **AI 调用需要你自己的 MiniMax API Key**，不开就是纯本地功能（仍然完全可用）。
- **不做云端同步、社交、多车手管理**。这是刻意的取舍，不是遗漏。
- 内置训练器（TP Virtual）类功能不在范围内。

## 版本

当前 **V0.9.1**。开发分支 `v0.8.3-b1`。

### V0.9.1 做了什么

一句话：**V0.9.0 说"不编数据"，这一版是把说过的每一条都实际查了一遍，
发现还有一批漏网的，逐个堵上。**

这批修复大多不是我们自己发现的 —— 独立审查和实测端到端跑出来的。

#### 数据诚实性（最严重的一类）

- **训练处方不再按编造的 FTP 生成**（后端 5 处）。
  最严重的一处：`/api/phases/race-plan` 里 `latest_ftp.ftp_w if latest_ftp else 250`
  —— 一个**从没测过 FTP** 的用户，实测拿到一份 `current_ftp: 250`、
  7 个节点 `ftp_target` 全部 = 250 的完整比赛训练计划。
  **一份看起来完全正常、但每天强度都是错的处方。**
  现在改成：实测 FTP > 估算 FTP（明确标注）> **400 明确拒绝并引导去测**。
  另外 4 处是同一个病：`race_prep.py` 的 `ctl or 60`（零训练用户 `ctl=0`
  在 Python 里是 falsy，反向默认值照样生效）、`insights.py`、`periodization.py`
  里的 `or 200`（同一个概念散着 200/250 两个互相矛盾的魔数）、`erg.py`
  签名里的 `ftp: int = 250`（导出的骑行台课程每段瓦数全按它乘）。
- **readiness 分数在维度不全时封顶**。2/5 个维度可用时归一化能凑出 100 分
  "极佳"。现在按可用维度数封顶（实测：5/5 → 不封顶，4/5 → 90，3/5 → 80，
  2/5 → 70，1/5 → 60）；五维齐全时 cap = 100，**老用户分数一个字节都不变**。
- **`target_tss` 数据不足时是 `null` 不是 `0`**。`0` 看起来像"今天免练"，
  实际是"算不出来"—— `None` 让人停下来问，`0` 让人直接照着骑车。
- 顺带修了一个同类病：零训练用户的 `has_load_data` 被扫描器报成假警，
  真问题（`target_tss=0`）被噪声淹没。**扫描器报假警就是在削弱它的可信度。**

#### 前端

- **功率区间副标题不再把估算 FTP 说成实测**。Coggan 七区本身就是按 FTP 推的，
  那句"基于 FTP 280W"不是装饰，是用户理解整张图的依据。
  同一个文案在文件里出现了两处，我第一次只改了其中一处。
- **功率曲线图里的估算 FTP 参考线要标明**：标签 `FTP 280W` → `估算 FTP 280W`，
  颜色 绿 → 琥珀。组件不猜，由调用方明确告知是实测还是估算。
- 现在用的是早就写好的 `ftpLabel`（实测 / 估算 / 未设置 三态），
  并加了防同类测试：不允许再出现裸的 `基于 FTP {ftp}W` 模板。

#### 时区

- **全系统统一到本地日历日**，修掉"凌晨骑的车归档到前一天"。
  UTC+8 每天有 **8 小时**（00:00–07:59）落在这个缝里：FIT 存 UTC →
  剥掉 tzinfo → 按 UTC 日归档 → 而用户在看本地日，那天是空的。
  实测复现：上海时区 10-09 01:00 的车被记到 10-08。
- 修法是在**归档层**转换，不动存储：`start_time` 是绝对时间戳，存 UTC 是对的，
  要变的只是"用哪个日历日归档"。
- 这一条我自己第一遍修错了方向（把测试改成跟生产代码对齐，掩盖了问题）。

#### Windows 交付

- **周报 PDF 的中文字体加上 Windows 自带字体**（微软雅黑 / 宋体 / 黑体 / 等线）。
  原来的候选清单**三条全是 Linux 路径** —— Windows 上一个都不存在，
  注册全失败后静默退回 Helvetica，**周报中文全是乱码**。
  而诊断只报 WARN 不报 FAIL，没有任何门禁会拦住它，358 个测试也全绿，
  因为没有一个测过字体。
- 第二个坑：文件存在 ≠ 能用。`.ttc` 是字体集合必须给 `subfontIndex`，
  不然 Linux 上也一样失败。**找不到任何中文字体时现在打 ERROR 日志**，原来是静默 fallback。
- 验收脚本必须带 `--desktop`，否则 Windows 上没装 Node.js 会起不来。

#### 打包护栏

- `tools/package_source.py` 缺前端构建产物或知识库时**直接中止打包**
  （`static/index.html` 缺失 → 白页；知识库 < 100 个文件 → AI 检索没资料）。
  这两个坑都真实踩过：前端产物被 `.gitignore` 排除导致打包漏掉；
  359 个长路径文件在 `git ls-files` 逐行读取时被静默丢弃。

- 接口数 127→**133 操作 / 113 路径**、GET 75→**79**、覆盖率 46%→**44%**
  （按当前 OpenAPI 重数，58 这个扫描覆盖数没变）
- 测试文件数 30 → **38**（35 个 `test_*.py` + 3 个公共 fixture/helper）
- 测试用例数 358（`pytest --collect-only` 实测）
- 知识库 359 篇 / 361 个文件 —— 核对后属实，未改

> 那句旁边写的"46%" —— 58/133 只有 44%。**在一个卖点是"不编数据"的
> 项目里，自己 README 里的数字飘了，比不检查更糟。**
