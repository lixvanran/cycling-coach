## 二、本轮修的真 bug（都有测试锁死，180 passed / 0 failed）

全部属于同一类：**"1 样本 = 1 秒"的隐含假设** 或 **静默失败**。

| # | 位置 | 症状 |
|---|---|---|
| 1 | `core/metrics/power.py` `normalized_power` | 零填充 → 10s 采样 NP 只有真值 1/10（2s 就腰斩） |
| 2 | `power_zones` / `power_zones_detailed` / `total_kj` / `hr_zones` | `mask.sum()` 数样本当秒 → 少算 10 倍 |
| 3 | `pa_hr_decoupling` | 门槛 `len(valid)<1800` → 1 小时骑行被当 6 分钟拒算 |
| 4 | `data/parsers/fit_parser.py` `position_lat/long` | 没从 semicircles 换算（潜伏 bug） |
| 5 | `fit_parser` 缺 session 汇总 | 静默返回 0，watcher 还报"导入成功" |
| 6 | `ai/m3_client.py` | `[THINK]` 裸 token + 降级提示泄漏给用户 |

新增共享工具 `sample_durations()` / `seconds_in_bins()`（power.py），hr.py 复用。
dt 用**区间模型**（每样本负责到下一点那段）而非梯形积分 —— 梯形会少算 1 秒。

**实测效果**（同一小时骑行，只改采样率）：

| 指标 | 修前 @10s | 修后 |
|---|---|---|
| `power_zones` Z4 | 360 秒 ❌ | **3600 秒** ✅ |
| `total_kj` | 90 kJ ❌ | **900 kJ** ✅（真值 250W×1h） |
| `pa_hr_decoupling` | 判"数据不足"拒算 ❌ | **正常计算** ✅ |

这正是 TP 用户说的 "zones waaayyy off"。**我们修了，TP 还没修。**

## 三、一次误判的教训（重要）

我曾报 P0-1「FIT 时长被放大 1000 倍（毫秒当秒）」—— **这是错的**。

决定性实验：

```
fit_tool 传 3600  → fitparse 读回 3600.0   (秒)
fit_tool 传 30600 → fitparse 读回 30600.0  (米)
```

fitparse **已经**应用了 profile 的 scale，直接返回人类单位。
现象的真凶是**我的测试 fixture 自己写了 `duration*1000` 造成双倍缩放**，然后我怪了 parser。

**教训**：合成测试数据前，先做"决定性实验"确认工具的单位约定，
别把自己的 fixture 当 ground truth。已把踩坑写进 `tests/fit_fixtures.py` 文档。

# 追加二：Windows 交付硬化（夜间自主批次）

日期：2026-10-03 夜
范围：Windows 启动/停止/诊断/卸载全链路 + 数据库升级安全

起因：上一轮把代码层的窟窿补完后，**最大的剩余不确定性是"在真机 Windows 上
到底跑不跑得起来"**，而沙箱是 Linux，验证不了。所以这一轮不加班功能，
专门拆 Windows 特有失败模式，并造一个让用户能自助验收的工具。

方法：主攻 + 独立 Verifier 对抗性审计（只读，产问题清单不修代码）。
Verifier 与我的实现互相独立，抓到了我写的代码里的真问题。

## 一、Verifier 抓到的、我自己没看到的

| 级别 | 问题 | 位置 |
|---|---|---|
| **P0** | `build_release.py` 用 `git ls-files` 收集文件、尊重 `.gitignore`，而 `cycling_coach/static/` 被 ignore → **官方 source zip 不带前端产物** → Windows 用户双击 start.bat 必失败，报错还让他去装 Node（而 start.bat 文件头承诺不需要 Node） | `tools/build_release.py:56-96` |
| **P1** | `kill_port()` 按英文串 `"LISTENING"` 过滤 netstat —— **该字符串在中文 Windows 上是本地化的**（输出 侦听/监听）→ 对本项目主力用户群等于静默失效 | `tools/start.py:731` |
| **P1** | 迁移前备份用 `shutil.copy2` 拷 WAL 模式的库 —— 未 checkpoint 的数据在 `-wal` 里，拷出来可能是空库。**空备份比没备份更坏**，它让用户以为有退路 | `database.py:335`（我当晚新写的） |
| **P1** | `diagnose.bat` 把 stdout 重定向成 diagnose.log 再打开，而 `diagnose.py` 真正写的是别处的 diagnose.txt → **用户打开的是一行"报告已写入"**，排障工具本身是坏的 | `tools/diagnose.bat:25-29` |
| **P1** | `uninstall.bat` 执行 `taskkill /F /IM node.exe /T` 和 `/IM electron.exe /T` → 杀掉用户机器上**所有** node/electron 进程（含其开发服务器、VS Code 工具链），且 `2>nul` 吞掉全部提示 | `tools/uninstall.bat:66-70` |
| **P1** | `stop.py` 的 `tasklist` 用 `text=True` 不给 encoding → 中文 Windows 上非 ASCII 进程名导致 UnicodeDecodeError；它继承 `ValueError` **不是** `OSError`，原 except 接不住 → stop.py 直接崩 | `tools/stop.py:49-60` |
| P2 | `file_sha256` 在 ORM 声明了 `index=True` 但 `_ensure_indexes` 补索引清单漏了它 → 老库升级后上传去重全表扫描 | `database.py:272-278` |
| P2 | `init_db()` 在 `main.py` 的 try 块之外 → 任何 DB 异常直接杀掉应用生命周期，用户看不到原因 | `main.py:66` |
| P2 | `repair_db` 的 `PRAGMA table_info` 没有 try 包裹（`_auto_migrate` 有）→ 新库上产出一整屏 FAIL 噪音 | `database.py:156-165` |

**Verifier 明确判定"已检查、无问题"的**（避免我按错误猜测去改）：
`%errorlevel%` 展开时机（无延迟展开陷阱）、`^` 转义、`findstr /C:` 用法、
`cd /d "%~dp0\.."` 路径引号（中文/空格用户目录安全）、.bat 无 BOM 是正确选择、
列迁移本身幂等且非破坏性（200 行老数据一条不少，第二次运行新增列数 = 0）。

它也纠正了我一个判断：原来的 `f":{port}" in line` 子串匹配**不会**把 18765
误判成 8765（前导冒号已锚定端口边界）—— 真正的坑是本地化字符串。

| 问题 | 修法 |
|---|---|
| `.gitattributes` 写 `*.bat text eol=lf` | 改 `crlf`；5 个 .bat 全部转 CRLF（143 行总计）。这是项目里一个**明确的错误配置**，不是风格问题 |
| `start.py` 没有 `--port` / `--no-browser` | 注册。argparse 原本直接报 "unrecognized arguments" 退出，用户看到的是"启动器坏了" |

## 三、新交付物：真正的自检工具

旧 diagnose.py 检查 node/npm/pnpm/esbuild/vite —— 而 Windows 正式用户
不需要 Node。用户遇到问题跑自检，工具报一堆"Node 正常"，真正让他打不开的
东西（静态资源、数据库、数据目录、端口）一个都没查。

新 `tools/diagnose.py` 按"用户会先撞上的顺序"查 7 项，核心是第 6 项：
**进程内起 TestClient 真的打一次 `/api/health`** —— 不是看日志猜。

```
1. Python / venv / 关键依赖       装得上吗
2. 前端静态资源 + 资源引用完整性    打不打得开界面
3. 数据目录 + 可写性               数据在哪、能不能写
4. 数据库建表/迁移/可读/记录数     库能不能开、数据在不在
5. 端口（精确匹配 + 占用者 PID）   被谁占了
6. 进程内起后端打 /api/health      环境问题还是代码问题
7. 最近的错误日志
```

**验证过的故障注入**（一个从不报错的检查等于没有检查）：
删掉两个静态目录 → 报 `[FAIL] 前端 build 产物` + 给出可执行修复 + 退出码 1。

## 四、老用户升级路径：从没测过，现在测了

V0.9.0 之前**所有** 200 个测试用的都是全新空库。
"用户从 V0.8.1 升级到 V0.9.0"这条事故率最高的路径**从来没被测过** ——
而老库的 `activities` 表没有 `file_sha256`，ORM 读它会 `no such column` → 全站 500。

新增 `tests/test_migration_upgrade_v090.py`（8 个），用**真实旧 schema** 建库塞数据：
新增列到位 / 数据一条不丢 / 老行为 NULL 不报错 / 迁移前有备份且是迁移**前**的表 /
干净库不产备份垃圾 / 连跑三次幂等 / WAL 未 checkpoint 时备份仍有全部数据。

> 其中 "WAL 未 checkpoint 时备份仍有数据" 这条**当场抓到我自己的 bug**：
> 第一版备份目录固化在 import 时的 `settings.workspace_dir`，
> engine 一旦被重绑（测试 / 多 workspace），备份就存到错误的目录。
