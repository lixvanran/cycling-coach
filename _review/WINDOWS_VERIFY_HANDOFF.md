# Cycling Coach V0.9.0 — Windows 真机验证对接说明

> 写给本地 Agent 执行的说明。目标是在**真实 Windows 机器**上验证
> 这个只能交付静态检查结果的沙箱产物。
>
> 仓库：https://github.com/lixvanran/cycling-coach
> 分支：`v0.8.3-b1`（HEAD = `16a9089`）
> 目标：让 Windows 正式用户**双击一个 .bat 就能用**，不需要装 Node。

## 0. 先说清楚：为什么这次验证重要

V0.9.0 之前的所有工作都在 Linux 沙箱完成。Windows 相关的东西
（`.bat`、CRLF 行尾、静态资源路径、端口占用）**全部只做过静态检查**，
从未在真机上跑过。

对一个 Windows-only 产品，这是最大的敞口。你的验证结果会直接决定
V0.9.0 能否发布。

**请如实报告失败，不要为了让流程走完而说"基本正常"。**
一个被明确记录的 bug，价值远大于一句"差不多能跑"。

## 1. 环境准备

### 1.1 克隆

```bash
git clone https://github.com/lixvanran/cycling-coach.git
cd cycling-coach
git checkout v0.8.3-b1
```

确认 HEAD 应该是 `16a9089`：

```bash
git log --oneline -1
# 期望: 16a9089 docs(V0.9.0): 记录第三轮 — 修过头与假信号变异测试
```

> **如果 clone 卡在 SSL 证书错误**：某些环境走 TLS 中间人代理。
> 试 `git -c http.sslCAInfo=<该环境的网关 CA 路径> clone ...`。
> 沙箱里用的是 `/etc/ssl/certs/agent-identity/sandbox-gateway-ca.crt`。

### 1.2 Python

- **要求 3.11 或更高**
- 先查：`python --version`
- 如果没有，从 https://www.python.org/downloads/ 装
  - ⚠️ 安装时**务必勾选 `Add Python to PATH`**
  - ⚠️ 这是 Windows 上最常见的失败原因

### 1.3 确认没有 Node（重要）

```bash
node --version
```

**V0.9.0 的核心交付目标是"正式用户不需要装 Node"。**
所以请**在没有 Node 的状态下验证**。如果机器上碰巧装了，先记下来，
但要明确告诉我"测试环境有 Node"——那这条验证就不作数。

## 2. 主流程验证（按顺序做，每步记录结果）

### 第 1 步：环境自检

双击 `tools\diagnose.bat`，或命令行：

```bat
tools\diagnose.bat
```

**期望**：输出一份自检报告，逐项显示 ✓ / ✗。
它会真的起一个后端、打一次 `/api/health`、检查前端静态资源是否存在——
不是只打印版本号。

**记录**：每一项的实际结果。哪一项 ✗，原样抄下来。

### 第 2 步：首次启动（干净模式）

双击 `tools\start.bat`。

**期望**：
1. 自动建虚拟环境、装依赖（第一次会慢，几分钟正常）
2. 端口 `8765` 上起后端
3. **浏览器自动打开** `http://127.0.0.1:8765`

**记录**：
- 首次装依赖有没有报错
- 浏览器有没有自动打开
- 页面有没有白屏

### 第 3 步：页面逐个打开

浏览器打开后，逐个访问并记录**任何一个**异常：

| 页面 | 地址 | 期望 |
|---|---|---|
| 首页 | `/` | 有内容，不白屏 |
| AI 教练 | AI 页 | **默认停在「训练答疑」**（第一个 tab），不是「随便聊聊」 |
| 数据导入 | 数据页 | 能打开 |
| 课程编排 | 新建课程 | **能打开，不报 `ReferenceError`**（见 §3.1） |
| 日历 | 日历页 | 有内容 |
| 赛事 | 赛事页 | 能打开 |

> **AI 页的默认 tab 是个重点**。V0.9.0 之前它默认落在「随便聊聊」，
> 招牌功能藏在第三个 tab 后面。这次修了，要确认修复生效。

### 第 4 步：零数据状态

**在导入任何数据之前**，回首页看"今日状态"卡片。

**期望**：
- readiness 显示 `--` 和「数据不足」
- **不是** 0 分，也**不是**任何具体分数
- 有一条说明为什么算不出来
- **不应该**出现 VO2max / 阈值间歇这类训练建议

> 这是 V0.9.0 修的核心 honesty bug 之一。之前零数据用户会拿到
> 82 分"极佳" + 高强度间歇处方。

### 第 5 步：导入真实数据

用你自己的真实 FIT 文件（码表导出的 `.fit`），走「数据 → 导入」。

**期望**：
- 导入成功，出现在活动列表
- **同一个文件再传一次** → 提示"重复"，不产生第二条活动
- 首页 readiness 卡片开始显示分数
- 分数下方显示「基于 N/5 维」（如果有维度缺失）

**记录**：
- 你的 FTP、导入了几次、有没有触发去重提示
- readiness 分数是多少、显示"基于几/5 维"

### 第 6 步：问 AI

在 AI 页的「训练答疑」tab 问一句，例如：
"我这周训练安排得怎么样？"

**期望**：回答里引用的数字**必须和面板上显示的一致**。

> V0.9.0 之前 AI 从来看不到你的 PMC 数据（`getattr(dict, ...)` 用法错误），
> 会反问用户"你面板是不是显示 CTL=0"——把我们的 bug 甩给你去检查。
> 这个问题必须确认修好了。

### 第 7 步：停止与重启

```bat
tools\stop.bat
```

然后重新双击 `tools\start.bat`。

**期望**：能正常重启。端口不被占用卡死。

> `stop.bat` 处理过 `UnicodeDecodeError`。如果这里报错，
> 是**乱码导致的编码问题**，请把完整的控制台输出（截图）发回来。

## 3. 已知的重点风险点

这几个地方在沙箱里**只做过静态检查**，请重点关注。

### 3.1 课程编排页曾会崩溃 🔴

**症状**：点进「新建课程」页，页面崩溃或控制台报
`ReferenceError: QUICK_TEMPLATES_WITH_ICONS is not defined`。

**原因**：一个常量定义在组件函数内部，却被同文件另一个模块级函数引用。
构建时 TypeScript 报了 `TS2304`，但之前一直没人跑 `npm run build`
（大家跑的是 `npx vite build`，**跳过类型检查**），所以错误攒了很久。

**已修**，但请务必确认第 3 步里这一项。

### 3.2 端口占用

后端用 `8765`。脚本会先尝试杀掉占用该端口的进程。

**风险**：`kill_port()` 之前用字符串匹配端口，可能误杀无关进程
（比如你自己开的 8765 开发服务）。已改成精确解析 + 只杀 Python 进程，
但**请确认它没有杀掉你不希望被杀的东西**。

如果你机器上 8765 被别的服务占着，先记下来，看看脚本的行为是否合理。

### 3.3 静态资源路径

后端要伺服 `cycling_coach/static/`（Vite 的 build 产物，已包含在仓库里）。

**期望**：不需要 `npm install`，不需要 `npm run build`，直接就能看到界面。
如果界面空白，**优先怀疑这里**——检查 `cycling_coach/static/index.html` 是否存在。

### 3.4 端口占用失败时"静默"启动

如果 8765 真的被占死，看看脚本是**明确报错**还是静默地用了别的端口。
静默换端口是坏体验——用户会以为自己在用 8765。

### 3.5 编码 / 乱码

`.bat` 全部是 CRLF 行尾（已用 `.gitattributes` 强制）。
`diagnose.bat` 里有 `chcp 65001`。

**如果控制台输出乱码**，请截图。Windows 中文控制台的编码问题很常见，
但我们改过 `stop.py` / `diagnose.py` 的编码处理，需要确认真的修好了。

## 4. 环境问题自查

| 症状 | 可能原因 |
|---|---|
| 双击没反应 | 没勾 `Add Python to PATH` |
| 端口被占用 | 上次没正常退出，跑 `tools\stop.bat` |
| 页面空白 | `cycling_coach/static/` 缺失，或代理拦截 |
| 装依赖失败 | 网络；国内可能需要换源（pip 换清华源） |
| 中文乱码 | 控制台编码；截图反馈即可 |
| 杀毒软件拦截 | Windows Defender 常误报 Python 脚本，需要加白名单 |

## 6. 一个悬而未决的产品判断（需要你拍板）

这个不属于 bug，是我们没把握的领域判断，**想听你的实际使用感受**。

### 减量周会被扣分

readiness 五个维度里，ACWR（急慢性负荷比）占 25 分。
它的评分规则是：ACWR < 0.6（过低）判 **0 分**。

**问题**：ACWR 0.42 左右通常是**计划内减量周的正常结果**——
你主动降负荷，急性负荷自然低于慢性负荷。此时判 0/25 相当于
"你的状态很差"，但实际上你正在做正确的事。

demo 数据就是这个情况：ACWR 0.42 → 0/25 → 分数被拉低。

### 这不是我能替你决定的

要修的话有两条路，风险不同：

| 方案 | 做法 | 风险 |
|---|---|---|
| A. 保持现状 | 不动，只在界面说明"减量期低 ACWR 属正常" | 低。但每逢减量周都会被扣分，你可能觉得分数"莫名其妙变差" |
| B. 引入 taper 检测 | 处于计划减量期时不惩罚低 ACWR | 更准，但要动阶段推导的逻辑链，可能引入新误判 |

**你实际用的时候，减量期被扣分能接受吗？**

如果你在做 Windows 验证时正好遇到减量周，看看那个分数和
"训练建议"是否让你觉得"不对，我明明在减量"。你的直觉比我的推理准。

（不急着现在回答，验证完再说也行，我只是不想它悄悄沉底。）
